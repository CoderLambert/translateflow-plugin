# YouTube Bilingual Subtitle Source

Issue #24 establishes the source boundary for the v0.8 YouTube subtitle pipeline. Issue #26 adds the current live-YouTube acquisition path without changing Provider translation, batching/cache orchestration, bilingual rendering, or player controls.

## Contract

Content-side source modules live under:

```text
src/content/subtitles/
├── source.js
├── youtube-bridge-protocol.js
├── youtube-timedtext.js
├── youtube-main-bridge.js       # MAIN world, injected by Background only
└── sources/
    ├── text-track.js
    └── youtube.js
src/background/youtube-bridge.js # validates sender/tab and installs MAIN files
```

A source emits normalized **cue snapshots**:

```js
{
  type: "cues",
  source: "youtube-timedtext" | "text-track" | "youtube-dom",
  reason: "cuechange" | "spa-navigation" | "dom-mutation" | "...",
  mediaId: "youtube:<video-id>" | "<media-url>",
  mediaTime: 12.34 | null,
  playbackRate: 1, // normalized to 0.25–4; invalid input defaults to 1
  observedAt: 1790000000000,
  track: {
    id: "...",
    kind: "captions" | "subtitles" | "",
    label: "English (auto-generated)",
    language: "en",
    mode: "showing" | "hidden" | "",
    autoGenerated: true | null
  } | null,
  cues: [
    {
      id: "stable-source-cue-id",
      startTime: 10.0 | null,
      endTime: 13.5 | null,
      text: "Normalized subtitle text"
    }
  ]
}
```

`mediaId` and normalized cue timing/text are the only source-level identity data #25 should need. YouTube CSS selectors are not part of the downstream contract.

## Source selection

### 1. MAIN-world player/timedtext bridge

The primary live-YouTube path runs in the page MAIN world because YouTube's player metadata and page fetch/XHR response objects are available there. The bridge:

- resolves the current player, video id, selected track and `getAudioTrack().captionTracks` metadata;
- observes page `fetch` and XHR calls whose URL path matches `/api/timedtext`; it reads the response body, but does not establish cryptographically that a matching request came from YouTube's player;
- parses only `response.clone()` / completed response data and returns YouTube's original request/response unchanged;
- uses Resource Timing only to notice matching requests and refresh player metadata; it never reads cue bodies from Resource Timing or refetches a caption URL;
- binds every response to `videoId + generation + trackRevision` and the selected track captured at request start; rejects late responses after video or track changes, including same-video A → B → A track changes. A URL with language metadata must match the selected language and human/ASR kind;
- after a one-second wait without a captured body, can call the YouTube player's caption module and select a track once for that video generation. Current YouTube Web subtitle requests may require a video-bound `pot`, so TranslateFlow passes only stable selection metadata (language plus ASR kind when applicable) to `setOption` and deliberately does not pass a captured/unsigned `baseUrl`; the YouTube player remains responsible for constructing the actual signed timedtext request. TranslateFlow does not author a timedtext fetch, manufacture a PO token, or nudge while subtitle mode is `off`.

The Background validates the sender tab and YouTube video-page URL before installing the bridge with `chrome.scripting.executeScript({ world: "MAIN" })`. The MAIN/ISOLATED channel uses a versioned, schema-validated `window.postMessage` envelope, with a 2 MiB serialized-payload limit. This is not an authenticated channel: page scripts can observe and forge page messages, so the isolated source treats all envelopes as untrusted input. The bridge exposes no callable `chrome.*`, Provider, cache, storage, or extension network capability to page scripts.

`TIMEDTEXT` currently includes normalized cues and track metadata plus a `requestUrl` string truncated to 2,048 characters. The URL may contain rotating signatures or PO-token query parameters. It is not copied into normalized snapshots, subtitle requests, cache identity, or Provider input; the parser's stable track identity ignores signed URL parameters. Do not log or persist the raw request URL.

`youtube-timedtext.js` is pure and supports JSON3, XML and srv3. Track identity uses stable language/kind/vss-id fields and ignores rotating signed URL / PO-token parameters.

### 2. Standards-first TextTrack fallback

`HTMLMediaElement.textTracks` is the preferred standards-based fallback when the current-generation MAIN timedtext path is unavailable. The adapter:

- considers only `captions` / `subtitles` tracks;
- consumes tracks already in `hidden` or `showing` mode;
- listens to `cuechange` and `TextTrackList` add/remove/change events;
- emits `activeCues` with start/end timestamps when the browser exposes them;
- does **not** force a disabled track to `hidden`/`showing`.

The passive-mode rule matters because changing `TextTrack.mode` can change host-player behavior. TranslateFlow should observe an already-active track instead of silently enabling captions.

Reference: MDN documents `HTMLMediaElement.textTracks` as a live `TextTrackList`, with track additions/removals reported by the list.

- https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/textTracks
- https://developer.mozilla.org/en-US/docs/Web/API/TextTrackList

### 3. YouTube DOM fallback

The arbitration order is: a successfully parsed current-generation MAIN timedtext body, then non-empty active cues from an enabled TextTrack, then rendered YouTube caption DOM. Once a timedtext body is accepted it remains the selected source even when no cue is active at the current media time; in that case the emitted snapshot has no active cues instead of switching to a lower-priority source. TextTrack tracks are limited to `captions` / `subtitles` in `hidden` or `showing` mode, with preferred-language match first, then `showing`, then track-list order. Disabled tracks are not enabled. If TextTrack has no active cues, the DOM is used.

YouTube's rendered caption DOM remains the final compatibility fallback. The adapter keeps these heuristics local to `sources/youtube.js`:

- player root: `#movie_player` / `.html5-video-player`;
- video: `video.html5-main-video` with generic `video` fallback;
- caption container: `#ytp-caption-window-container` / `.ytp-caption-window-container`;
- caption text: `.ytp-caption-segment`, current visual-line and captions-text descendants.

Caption selectors are ordered alternatives. The adapter uses the first non-empty selector result instead of joining both a segment and its parent visual line, which would duplicate the original text. The rendered host exposes the selected source as `data-tf-subtitle-source` for DOM inspection without exposing bridge URLs or credentials.

These are **private YouTube implementation details**, not the primary acquisition API. A selector change must be fixed only in the YouTube adapter; #25/#26 must not depend on them for network acquisition.

When a source is active and mode is not `off`, the adapter hides the caption container's native visual layer while TranslateFlow renders its cue layer. The change is limited to CSS visibility and is restored on off/stop/teardown; it is never used to acquire cues.

For a captured timedtext track, snapshots keep active cues in `cues` and separately expose `upcomingCues`. At normal speed the window remains five known timestamped cues within twelve media seconds. The source scales the time horizon with `playbackRate` (up to 48 media seconds), with five to ten future cues; at double speed it permits ten cues within 24 media seconds. This preserves up to twelve wall-clock seconds of lead time when the cue-count limit allows it. Invalid rates default to one; rates are bounded to 0.25–4. Both timeline selection and repeated snapshot normalization apply the same window. Enabled TextTracks provide that window from their full cue list and refresh immediately on `ratechange`, keeping stable cue IDs before and during playback. DOM fallback cannot provide a future window. Only active cues are rendered; the complete transcript is never displayed or sent to the Provider.

The source updates on `timeupdate`, seeking, play/pause and rate changes, with one timer for the next cue boundary while playing. Paused/seeking media does not schedule that wall-clock timer; media events resume scheduling. Snapshots carry the live `seeking` flag so a seek revokes pending work within the same video/track.

The existing mode/preset/size controls are hidden until the user opens the `译` button in YouTube's bottom `.ytp-right-controls`, before the native settings button. The compact panel opens above the control bar, inside the existing subtitle Shadow DOM. Escape closes it and restores focus; clicking outside or changing fullscreen closes it. A renderer-owned child-list observer reattaches the same live button after native controls reconstruction and removes stale cloned entries. It disconnects on unmount, along with document click/keyboard/fullscreen handlers. A small bottom-right fallback entry is used only while native controls are absent. Player remounts rebuild and localize the preset options. No new translation scheduler or MAIN capability is involved.

## SPA and teardown behavior

YouTube changes videos without a full document reload. The source and bridge therefore:

- listens to `yt-navigate-finish` and `yt-page-data-updated`;
- listens to browser `popstate` as a generic route-change signal;
- re-resolves the player/video on each refresh;
- tears down the previous TextTrack listeners when the `<video>` element is replaced;
- rebinds its player-root MutationObserver when a refresh detects a new root;
- removes its fetch/XHR wrappers and disconnects listeners/observers when the bridge receives `STOP`.

YouTube video identity is derived from `?v=`, `/shorts/<id>`, `/embed/<id>`, `/live/<id>`, or `youtu.be/<id>`. If no YouTube id is available, the current media URL is used as a fallback identity.

## Language and auto-caption metadata

Standard `TextTrack` gives us `language`, `label`, `kind`, `id`, and `mode`. The source normalizer preserves explicit `autoGenerated: true` and ASR kind, or derives `true` from an explicit auto/ASR id/label hint; otherwise the value is `null`, not `false`.

The MAIN bridge reports stable player track metadata, including `autoGenerated: true` for ASR/auto-generated tracks when YouTube exposes that hint. The DOM fallback cannot reliably recover source language or whether the visible caption is auto-generated from rendered text alone. It therefore reports empty language and unknown auto-generation metadata. Downstream code must not invent these values.

## Translation identity and invalidation

The controller checks media/track scope, active cue identity and live media time before displaying a result. The pipeline retains successful results within its bounded current scope, including DOM captions without timestamps. A → gap → A, A → B → A and original → bilingual can restore those results without a new Provider call. Local replay identity includes text; DB4 still receives its existing position/sequence identity and uses the existing effective-config cache identity.

For rolling YouTube DOM captions, the normal stabilization wait remains 280 ms, with an 800 ms maximum wait while words continuously append. A returned translation may remain visible while its entire original phrase is still present in the current caption on whitespace boundaries. Appending words does not erase that translation; removing the phrase, changing scope/configuration, seeking or clearing captions does. This fallback cannot anticipate unseen subtitles or guarantee delivery before a phrase scrolls out when Provider latency exceeds its visible lifetime. Timestamped cues retain their exact identity/time checks.

The subtitle effective-context request uses `surface: "subtitle"`, matching the existing AI/Chrome-local subtitle route rather than the independently selected page-translation method. Configuration and temporary-preset changes revoke old work and clear completed results before awaiting new context. Successful page/all cache removal broadcasts `CACHE_INVALIDATED`; matching subtitle controllers clear results without proactively retranslating. Subsequent authorized source observations can translate again.

The existing Translation Coordinator registers the subtitle consumer before configuration/cache awaits. Cancellation and config revision checks prevent a late preparation step from starting a Provider call or delivering a stale cache hit. Once a DB4 store starts, its existing write fence governs persistence; consumer cancellation does not promise rollback or prove the underlying execution resource has been released. The short-caption path uses the same single `processQueue` for current cues and bounded lookahead. Known timed cues skip DOM stabilization. A waiting current cue schedules dispatch without the future-work batching delay; each dispatch sorts current cues first and sends them separately from future cues. Overlapping current cues stay together within the existing batch limit. Future batches contain at most two cues, and queue pressure drops future work before current cues. Observations discard unstarted work outside the latest window. This trades additional requests for earlier current results and smaller amounts of future work ahead of newly current cues; a slow request already in flight still has to settle. After seek/cancellation no replacement execution starts until the old transport settles; no additional scheduler, cache or concurrent prefetch executor is introduced. Playback rate is a local snapshot field only; it does not change Provider messages, cache identity or persistent schemas.

Failures have per-result bounded retry cooldowns of 2/5/15/30 seconds. Only failures of currently active cues produce the translation-unavailable status; a failed future cue cannot overwrite the status of a successful current translation. Successful overlapping cues remain reusable, and failure of an old cue does not block a newly queued cue. Retry requires another source observation after cooldown or a mode change; there is no automatic retry timer or new retry button.

## Verification

The deterministic unit tests cover JSON3/XML/srv3 parsing, envelope validation and size limits, YouTube-tab installation, fetch/XHR wrapper preservation and teardown, nudge behavior, stale-video rejection, active-cue scheduling, source fallback ordering and SPA refresh. The Playwright cases run the real extension against local fixture pages and mock responses; they do not connect to live YouTube.

Run the repository checks and focused YouTube browser cases with:

```bash
npm run validate
npm run build:extension:wxt
TF_TEST_WORKERS=1 npm run test:e2e -- e2e/youtube-subtitles.spec.mjs e2e/subtitle-pipeline.spec.mjs --retries=0
```

At the reviewed baseline, the quality and Chromium E2E workflows use `workflow_dispatch`; their presence does not prove a PR has run either check. Since fixture tests cannot cover YouTube's live player, manually smoke-check the actual candidate/package on real YouTube before release; results can vary by account, region and player rollout. The current uncommitted reliability-slice evidence and remaining limits are recorded in [the implementation report](tasks/youtube-subtitle-reuse-v1/implementation-report.md); the earlier validation report remains bound to the original candidate.

Before each v0.8 release candidate ships, perform a manual smoke check on real YouTube for:

1. human subtitle track and original/bilingual render;
2. auto-generated/ASR subtitle track;
3. language/track switch;
4. captions off -> native behavior restored and no nudge;
5. watch-page SPA A -> B with no stale cue/translation;
6. theater/fullscreen player replacement or relocation;
7. Provider failure keeps the original cue visible;
8. repeat/cache path makes no unnecessary Provider request.

## Contract for #25

The stabilization/batching/cache pipeline should consume only normalized snapshots and should:

- key video/session identity from `mediaId` plus effective source/track metadata as needed;
- treat snapshots as current observations, not final sentence boundaries;
- merge rolling/overlapping cue text without relying on DOM node identity;
- use timestamps when present but support `null` timestamps from DOM fallback;
- invalidate/reset stabilization state when `mediaId` changes;
- keep Provider/cache work outside the source adapters.

No IndexedDB schema, cache fingerprint, Provider path, manifest permission, or production UI changes are introduced by #24.
